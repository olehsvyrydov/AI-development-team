## D-009 — Knowledge base / memory: integrate existing tools, don't build an engine (2026-06-08)

Decision (user-ratified): the knowledge base keeps the **zero-config local markdown vault as the default** (works offline, no account, no egress — agents read the files directly). Heavy lifting is delegated to **existing OSS local tools as OPTIONAL overlays**, connected by URL/endpoint — never required:
- **Obsidian** — the project's markdown KB *is* an Obsidian vault; point Obsidian at it for the graph/UI; optionally surface a link/embed in the Base panel.
- **Self-hosted mem0 / OpenMemory** — optional semantic store + recall + the "did it interpret my note correctly?" Q&A, via MCP/API adapter. Local/self-hosted only (hosted services break the local-first / no-egress rule).

This supersedes the scope of backlog item **BL-02** (KB edit/delete + interpretation-check): rather than building KB CRUD + Q&A ourselves, BL-02 becomes "thin optional adapters + a connect-your-tool setting + link/embed", on top of the file default. Editing/deleting docs is then largely the external tool's job (or simple file ops on the vault); semantic Q&A is the mem0/OpenMemory adapter's job.

Rationale: avoids reinventing memory management; honours local-first/no-egress/zero-account; the only DART glue is a small adapter, because the integration point that matters is that the main tool (Claude Code/Kiro) can read the knowledge — files need no glue, mem0/OpenMemory need one thin MCP/API adapter.
